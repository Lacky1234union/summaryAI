## 2026-10-29 — Пустой конспект — ошибка с повтором; рассуждение OpenRouter выключено (#63)
_Дополнено 2026-11-03: обрез лимитом, пустой ответ судьи, промпт `lecture` v4._
**Контекст:** на живом созвоне DeepSeek V4.1-Flash через OpenRouter вернул документ строго по
схеме, но пустой (заголовок и пустые списки). Схема его пропускает, конвейер принял его за
саммари, и рендер перезаписал хорошую заметку из прошлого прогона. Повторы: с рассуждением пусто
в 5 из 6, без — в 1 из 4 (BENCHMARKS, #63).

**Решение:**
- Документ всей записи без единого утверждения (у `raw` — без блоков) — не саммари: до двух
  повторов запроса (`EMPTY_RETRIES`), затем `SummaryFormatError`. Артефакт не пишется — заметка
  остаётся прежней. Карты окон не проверяются: окно тишины пустым быть может. Заглушка `echo`
  пустая по определению — её не проверяем.
- `SUMMARY_VERSION` 4: пустые саммари, уже лежащие в кэше, иначе отдавались бы дальше.
- `SUMMURAZE_LLM_OPENROUTER_REASONING`, по умолчанию `false` → `reasoning: {enabled: false}`;
  пусто — не передавать. Значение — в ключе саммари и проверки, только для OpenRouter.

**Причина:** пустой ответ — сбой провайдера, а не содержание: пропущенный, он стоит заметки.
Повтор дешёвый ($0.005), и OpenRouter может отдать его другому провайдеру. Рассуждение — сама
причина у DeepSeek и лишние токены.

- Ответ, обрезанный лимитом (`finish_reason: length` → `LLMResult.truncated`), — один повтор с
  лимитом вдвое, но не больше остатка контекста; второй обрез — `SummaryFormatError`. Ответ не по
  схеме без обреза не повторяется: это сервер без structured outputs, повтор не поможет.
- Ответ судьи не по схеме (пустая строка) — переспрос в пределах `verify.RETRIES`, а не падение
  проверки с первого раза.
- Промпт `lecture` v4: «пустой список — правильный ответ» — только для необязательных разделов;
  `tldr` и `sections` заполняются всегда.

**Последствия:** все прошлые саммари при повторном `run` запрашиваются заново (версия). Качество
без рассуждения на длинной лекции сверено 2026-11-03 (71 мин, BENCHMARKS): не хуже, в 4 раза
дешевле. Лимит ответа в конфиг не выносили: без рассуждения 16k хватает с запасом (4.8k на
71 мин), а обрез теперь лечится повтором.

## 2026-10-29 — Веб — читатель SQLite и кэша; прогресс пишет оркестратор (#23)
**Контекст:** третий интерфейс к тому же ядру (ADR 2026-10-26): список записей, страница с
конспектом, транскриптом и плеером, прогресс долгой стадии. Конвейер уже пишет всё нужное в SQLite
и кэш стадий, кроме одного: какая стадия идёт *сейчас* — `stage_runs` пишется по её окончании.

**Решение:**
- `summuraze web` — FastAPI + uvicorn, одна страница на чистом JS, без сборщика фронтенда.
  По умолчанию `127.0.0.1:8765`; другой адрес — с предупреждением: пароля нет.
- Веб **читает** ту же SQLite и кэш артефактов, своей копии данных у него нет. Транскрипт и
  конспект — из артефактов последнего успешного прогона (`summary.json`, `verify.json`), а не из
  заметки: Markdown обратно не разбираем. Поверх транскрипта — то же, что делает оркестратор:
  замены терминов из манифеста саммари (`--terms` курса больше нигде не записан) и детектор #12.
- Миграция 4: у прогона `profile`, `stage`, `stage_started_at`, `pid`. Оркестратор отмечает начало
  каждой стадии — прогон, запущенный из терминала или меню, виден в браузере со стадией и
  секундомером. `running` с мёртвым `pid` — «прервано» (убит, ноутбук выключили).
- Список: статус — последнего прогона; профиль и модель — прогона, чей конспект показан; цена —
  сумма всех прогонов записи (прогон из кэша стоит $0, цена последнего соврала бы).
- Документ отдаётся разделами и пунктами с таймкодом в секундах и пометкой проверки — порядок и
  отсев повторов как в итоговой заметке (#50): браузер и Obsidian показывают одно и то же.
- Плеер: сжатое аудио заметки → wav ингеста → оригинал, что уцелело; `FileResponse` с `Range` —
  иначе не перематывает. Пока прогон идёт, страница обновляет только строку статуса: перерисовка
  сбросила бы плеер.

**Причина:** один источник истины — нет рассинхрона между тем, что видит терминал, браузер и
Obsidian. Прогресс в БД, а не в памяти процесса: тогда неважно, кто запустил прогон.

**Последствия:** запуск прогона из браузера и переключатель провайдера с ценой — следующий шаг
#23: процессу веба придётся спрашивать согласие на отправку (#20) сам, терминала у него нет.
Прогоны до миграции профиля не знают — в списке «—». У записи с двумя профилями страница
показывает конспект последнего прогона.

## 2026-10-29 — verify: судья — та же модель по тому же префиксу; «неразборчиво» — без модели (#22)
**Контекст:** таймкод-ссылка делает проверку утверждения дешёвой, но человек проверяет выборочно.
Нужен проход, который проверяет всё и показывает, чему в документе не верить. Своей модели
(#19) лишний проход стоит минут, API — копеек.

**Решение:**
- Отдельная стадия `verify` после `summarize`, со своим артефактом (`verify.json`) и ключом от
  ключа саммари: включение проверки не пересчитывает конспект, правка промпта судьи — только её.
- Судья — **та же LLM, тот же префикс** (транскрипт байт в байт): у DeepSeek кэш-хит, у своей
  модели KV поднимается из слота; модель одна на обе стадии — `llama-server` не стартует дважды.
  Длинная запись — окнами, как у саммари, каждому окну — утверждения из его ядра.
- Вердикт по каждому утверждению: таймкод доказательства (первым полем — сначала найди, потом
  суди), «да / частично / нет», причина до 100 символов (лимит в схеме — грамматика llama.cpp).
  Доказательство далеко от таймкода утверждения → «таймкод ведёт не туда»: факт верен, ссылка нет.
- Судья промолчал про часть утверждений — переспрашиваем только про них, до двух раз; дальше
  «не проверено», а не «подтверждено».
- Без модели: утверждение без таймкода; «неразборчиво» — по записи (пометка детектора #12 или
  ≥ 2 слов с уверенностью Whisper < 0.4 в пределах 30 с).
- Пометки — после таймкода строки заметки (❌ нет в записи, ◐ частично, ↪ ссылка на место, где
  сказано, ❔ не проверено); подтверждённое — без пометки. Сводка — callout в начале заметки и
  `verified: "N/M"` во frontmatter.
- Сбой проверки не стоит заметки: предупреждение, заметка без пометок, в кэш сбой не попадает.
- `SUMMURAZE_VERIFY_ENABLED=false` выключает стадию.

**Причина:** отдельная модель-судья — ещё 2–5 ГБ и ещё один старт на этом железе; NLI-модели
для русского на CPU не дают ничего лучше LLM. Своя же модель с найденной строкой-доказательством
ловит главное — выдуманные пункты (цвета трёхцветного алгоритма, неразборчивое место Qwen3-8B,
«фоновый режим» GC). Пункты «неразборчиво» Qwen3-4B проверять не умеет: называет «голланд»
искажением в причине и ставит «нет», — а уверенность слов Whisper отвечает на этот вопрос точно.

**Последствия:** судья строгий — обещание лектора «разберём X» засчитывает как «нет» тезису
«X разбирается»; ложные тревоги дешевле пропущенной выдумки, но читателю видны. Своей модели
проверка добавляет 2–4 минуты на трёхминутную лекцию (вердикты — генерация). Доля
подтверждённых и ручная сверка — BENCHMARKS.md; пересмотреть на фикстурах #8.

## 2026-10-28 — Своя модель: llama-server на время стадии, Vulkan, Qwen3-4B (#19)
**Контекст:** режим, в котором запись не покидает машину. Железо — 14 ГБ общей памяти, ~7 ГБ
свободно, Ryzen 7 5700U с Radeon Vega 8. Whisper и 8B-модель вместе не влезают.

**Решение:**
- `llama-server` напрямую, а не ollama: на слой меньше, тот же OpenAI-совместимый API (адаптер
  прежний), есть `/tokenize` для бюджета (#16) и слоты для кэша промпта.
- Сервер поднимает **фабрика** LLM — то есть после ASR — на свободном порту 127.0.0.1, и гасит
  оркестратор сразу после саммари (`LLMProvider.close`). Постоянный демон держал бы 4–7 ГБ всё
  время транскрибации. Порядок «ASR выгружен → сервер запущен → сервер погашен» — тест.
- `--local` = `Settings.localized()`: та же секция `llm` с локальным адресом и `server`, плюс
  `--local-only`. Настройки — `SUMMURAZE_LOCAL_LLM_*` (модель, бинарь, контекст, потоки, флаги).
- Флаги: `--parallel 1`, `-fa on -ctk q8_0 -ctv q8_0` (KV вдвое меньше), `--cache-ram 0`,
  `--alias <имя файла>`.
- Кэш промпта между прогонами: сервер живёт одну стадию, его кэш умирает с ним — KV слота
  сохраняется на диск после запроса и поднимается перед запросом с тем же префиксом
  (`--slot-save-path`, `/slots/0?action=save|restore`). Последние 2 файла (~1.5 ГБ на час).
- **Vulkan-сборка** llama.cpp: на встроенной графике промпт в 4–6 раз быстрее CPU, генерация в
  1.5 раза. Слои на GPU раскладывает сам сервер (`-ngl auto`).
- **Модель — Qwen3-4B-Instruct-2507 Q4_K_M, контекст 32k** (замер против YandexGPT-5-Lite-8B и
  Qwen3-8B в BENCHMARKS.md): вдвое быстрее 8B на промпте, на 1.5–2.5 ГБ легче, по содержанию
  полнее; вымысел — в мелочах. Qwen3-8B выдумал целый пункт и занимает 6.6 ГБ из ~7.

**Причина:** время локального саммари почти целиком — обработка промпта и генерация; на этом
железе их решает iGPU, а не число параметров. 4B на GPU успевает больше, чем 8B на нём же.

**Последствия:** `--local` — второй класс по качеству: проверять по таймкодам. Выбор модели
предварительный — одна трёхминутная лекция; пересмотреть на фикстурах #8. Двухчасовая лекция —
по расчёту ~20 мин (окна #21), не замерено.

## 2026-10-28 — Длинные записи: карта по окнам, итог по карте (+ транскрипт, если влезает) (#21)
**Контекст:** после #16 запись, которая не влезала в один запрос, получала отказ. У DeepSeek
(1M) это многочасовой семинар, у локальной 8B-модели (8–32k) — обычная лекция. Свёртка
«пересказ кусков → пересказ пересказов» теряет связи начала с концом (ADR «Single-pass как
основной режим»).

**Решение:**
- Окна — по границам сегментов, под порог из `budget` за вычетом промпта карты. Разрез в
  последних 15 % окна: после конца предложения, без точек — на самой длинной паузе. Перекрытие —
  ~10 %, до 20 %, если так дотягиваемся до начала фразы.
- Проход 1: окно → `WindowMap`: темы с таймкодом начала, в них утверждения с таймкодами, плюс
  «открытые нити» (вопрос без ответа, «вернёмся к этому», введённое обозначение).
- Склейка: утверждение принадлежит окну, в чьё **ядро** (без перекрытия) попал его таймкод —
  перекрытие даёт контекст, но не дубли; тема, продолжившаяся через границу, сливается.
- Проход 2: документ профиля по карте. Если карта + полный транскрипт влезают в **контекст** —
  с транскриптом (первым, байт в байт: кэш префикса тот же), иначе — по одной карте. Порог второго
  прохода — контекст без `SINGLE_PASS_MAX`: тот означает «без опоры модель теряет середину», а с
  картой опора есть. Так `SINGLE_PASS_MAX` даёт режим «карта + транскрипт», а нехватка
  контекста — «по карте».
- `raw` второго прохода не делает: блоки окон склеиваются по ядрам.
- Не влезает даже так (окно меньше 1000 токенов, карта больше контекста) — отказ с подсказкой.
  Контекст меньше 4096 — отказ ещё в preflight, до ASR. Грубая проверка по длительности речи
  из #16 убрана: длинная запись теперь не повод для отказа.
- Токены строк — оценкой в масштабе точного счёта сервера (один `/tokenize` на весь транскрипт).
- Ключ кэша саммари получает `windows.VERSION` только у записей, которые могут пойти окнами
  (оценка больше половины порога): правка нарезки не сбрасывает кэш обычных лекций.
- В `summary.json` — `mode`, `windows`, `final`; usage и цена — сумма всех запросов.

**Причина:** итог пишется, когда модель видит структуру всей записи, а не по кускам: вопрос из
первого окна и ответ из последнего оказываются в одном запросе. Ядра окон делают таймкоды
непротиворечивыми без пост-обработки текста.

**Последствия:** окна дороже одного запроса (N+1 запросов, транскрипт идёт дважды). Склейка
проверена тестом на «конспектирующей» заглушке; качество на живой многочасовой записи — приёмка
пользователя: длинных записей пока нет.

## 2026-10-28 — Бюджет токенов: токенизатор сервера локально, замеренный коэффициент по API (#16)
**Контекст:** single-pass — основной режим, но порог зависит от провайдера: контекст 1M у DeepSeek
V4.1 Flash и 8–32k у локальной модели. Нужен счёт токенов и решение «один запрос или окна» до
отправки, а не 400 от сервера.

**Замер** (2026-10-28, DeepSeek V4.1 Flash через OpenRouter, `max_tokens=1`, живая русская
лекция, 3 мин): транскрипт с таймкодами — **3.19 символа на токен** (2.2 токена на слово),
сплошной текст — 4.29 (1.55 токена на слово). Таймкод `[ЧЧ:ММ:СС] ` — ~8 токенов на строку.
Плотность — 5.4 токена на секунду речи, ~19k на час речи. Схема ответа в `prompt_tokens` почти
не попадает: 1343 реальных токена при оценке 1354 без схемы.

**Решение:**
- `count_tokens` в протоколе LLM. Локальный сервер — его токенизатором (`POST /tokenize`
  llama.cpp); нет эндпоинта или сервер лёг — оценка. API — `None`: у OpenRouter и DeepSeek
  эндпоинта подсчёта нет.
- Оценка — `символы / 3.0`, с запасом к замеренным 3.19.
- Порог: `контекст − ответ − 64`, где ответ — `min(max_tokens профиля, контекст / 4)`; поверх —
  `SUMMURAZE_LLM_SINGLE_PASS_MAX`, если он ниже. `max_tokens` запроса = тот же резерв: на малом
  контексте 16k на ответ не съедают весь бюджет. В ключ кэша саммари он идёт, только если
  отличается от профиля — старый кэш жив.
- Решение печатается: «Саммари: один запрос: 1.4k из 984k токенов (оценка по символам; …)».
- Не влезает — `TranscriptTooLong` до отправки, со ссылкой на #21 (окна). До ASR — грубая
  проверка по длительности речи с нижней границей 3 токена/с: отказ, только если не влезет даже
  так, — час Whisper ради отказа не тратим.

**Причина:** точность важна там, где контекст мал, — и именно там (llama.cpp) есть точный
токенизатор. При 1M ошибка оценки в 10 % ничего не решает, а тянуть токенизатор DeepSeek
(версия для V4.1 не опубликована) ради неё — лишняя зависимость.

**Последствия:** режим «окна» пока отказ; #21 подставит вместо него двухпроходную схему.

## 2026-10-28 — Экспорт транскрипта рядом с записью; реплики субтитров по словам (#14)
**Контекст:** транскрипт — самостоятельный артефакт: его читают, ищут по нему, подкладывают
плееру. До #14 он жил только в кэше (`transcript.json`) и в заметке; `.srt` для Media Extended
делался «сегмент = реплика», а сегмент Whisper — до 30 с речи: строка уезжает за экран.

**Решение:**
- `summuraze transcribe` кладёт `запись.json/.txt/.srt` рядом с записью; `--format` (json, txt,
  srt, vtt, all), `--out` — другая папка. Без кода языка в имени: mpv и VLC сами подхватывают
  `запись.srt` рядом с `запись.mp4`. Формат проверяется до транскрибации.
- Реплика — до 2 строк по 42 знака и до 7 с показа, режется по пословным таймкодам, на конце
  фразы — охотнее; не короче 1 с, если не наезжает на следующую; границу сегмента не пересекает,
  чтобы `[?]` стоял ровно на сомнительном куске. Без пословных таймкодов время делится
  пропорционально длине слов. Те же реплики идут в `.srt` заметки Obsidian.
- TXT — абзацы с таймкодом начала: новый абзац по паузе ≥ 2 с, после 600 знаков — на конце
  фразы, после 1200 — на границе сегмента (Whisper на разговорной речи часто без точек).
- JSON — полный `Transcript` (слова, вероятности, флаги), кириллица без эскейпов.

**Причина:** один набор реплик для плеера и для Obsidian — одна логика и один тест. Пределы
42×2 / 7 с — обычные нормы читаемости субтитров.

**Последствия:** экспорт не кэшируется (рендер, дёшево) и не трогается `prune` — это файлы
пользователя. Тест сверяет таймкоды реплик с тем, как их читает демуксер ffmpeg (тот же, что у mpv).

## 2026-10-28 — `--local-only` в фабриках, согласие на хост, `is_local` по имени хоста (#20)
**Контекст:** guardrail #7 — запрет сети механизмом, а не предупреждением. До #20 противоречие
`local_only` + внешний URL ловил только валидатор конфига; фабрика LLM не проверяла ничего,
Whisper при первом запуске качал модель с HuggingFace. `is_local` искал `localhost` подстрокой URL —
`https://evil.com/?localhost` считался локальным.

**Решение:**
- `Settings.local_only` доезжает до секций `llm` и `asr` (валидатор конфига). Фабрика LLM
  (`check_llm`, и при прямом вызове `make_llm`) не создаёт провайдера с внешним адресом —
  `NetworkForbidden`. Whisper под запретом — `local_files_only=True`; нет модели на диске —
  `ASRModelMissing` с подсказкой.
- Флаг `--local-only` у `run`, `record`, `transcribe` — `Settings.restricted()`, та же проверка,
  что из `.env`. Отказ — до ингеста и до записи в истории.
- `is_local` — по `urlparse(url).hostname` из списка локальных имён.
- Согласие: перед первой отправкой на хост CLI показывает провайдера, модель и объём («текст
  транскрипта целиком, ~20 тыс. токенов на час; аудио — никогда»), спрашивает и запоминает в
  таблице `consents` (миграция 3). Спрашиваем **до** ASR — после часа Whisper человека у терминала
  может не быть. Без терминала и без согласия — отказ с подсказкой, а не тихая отправка.
- `summuraze log`: статус, длительность записи, время прогона, кэш; второй строкой — куда ушло
  (хост или «локально»), модель, токены вход→выход (кэш), цена; итог стоимости.

**Причина:** фабрика — единственный путь к провайдеру, значит единственное место, где запрет не
обойти. Согласие на хост, а не на проект: смена провайдера — новый получатель транскрипта.

**Последствия:** тест открывает 0 сокетов на полном прогоне под `--local-only` (подмена
`socket.connect`/`getaddrinfo`). Первый прогон на OpenRouter после обновления один раз спросит
согласие — из скрипта без терминала до этого он падает с подсказкой.

## 2026-10-28 — Заметка: итоговый вид по умолчанию, отладочный — по флагу (#50)
**Контекст:** первая живая заметка вышла «отладочной»: полный frontmatter с моделями и стоимостью,
все разделы подряд, длинный транскрипт со ссылкой на каждой строке. Пользователь: этот вид оставить
для отладки, итоговый — для чтения.

**Решение:**
- По умолчанию — итоговый вид: frontmatter `aliases` (тема лекции), `recorded`, `duration`,
  `audio`, теги `summuraze` + тип профиля; «Коротко» — `[!summary]`, глоссарий — `[!abstract]`,
  каждый вопрос — `[!question]`, «что почитать» — `[!info]`; «неразборчиво» и транскрипт —
  свёрнутые callout'ы; таймкоды `▶ 01:37` (после часа — `1:02:05`).
- `SUMMURAZE_NOTE_DEBUG=true` или `--debug` у `run`/`record` — прежний вид байт в байт.
- Содержание одно — разная подача: тот же `_Body`, та же дедупликация и пометка
  «⚠️ без таймкода» (guardrail #5).

**Причина:** согласовано на макете из живой лекции (2026-10-28). Глоссарий не таблицей: ссылка
`[[файл#t=…|метка]]` в таблице требует экранировать `|` — хрупко. Тема — в `aliases`, потому что
имя файла — дата и имя записи, а искать заметку будут по теме.

**Последствия:** рендер не кэшируется — переключение вида мгновенно пересобирает заметку из кэша.
`detach_audio` (#49) понимает оба вида: строка `audio:` во frontmatter одинакова.

## 2026-10-28 — Срок хранения: удаляется только звук, дата — из БД, выходы рендера — в БД (#49)
**Контекст:** ~30 часов записи в неделю. Оригинал (~29 МБ/ч в Opus после #37), wav ингеста в
кэше (~115 МБ/ч) и аудио в хранилище (~14 МБ/ч, на каждом устройстве LiveSync) копятся; текст —
килобайты. Пользователь хочет срок хранения и «удалить всё до даты».

**Решение:**
- `summuraze prune --before ДАТА | --older-than 30d` — по умолчанию только показывает план и объём;
  удаляет с `--yes`. Без флагов — срок из `SUMMURAZE_RETENTION_DAYS`.
- `SUMMURAZE_RETENTION_DAYS` — та же чистка в конце каждого прогона до заметки (`run`, `record`,
  меню); запись текущего прогона не трогается.
- Удаляется: оригинал — только из `SUMMURAZE_RECORD_DIR` (чужой — по `--include-foreign`; автосрок
  чужие не трогает никогда); кэш стадий `ingest` и `note-audio` — по ключам из `stage_runs`;
  аудио и `.srt` в хранилище. Транскрипт, конспект, заметка и история остаются.
- Рендер пишет свои файлы в новую таблицу `outputs` (миграция 2); `recordings.pruned_at` —
  отметка, что аудио удалено. Новый прогон той же записи снимает отметку.
- Заметка переписывается: таймкоды `[[x.ogg#t=…|ЧЧ:ММ:СС]]` → `` `ЧЧ:ММ:СС` `` (как при
  выключенном аудио), плеер → `> [!info] Аудио удалено ДАТА`, в frontmatter `audio_removed`.
- Дата записи — `recordings.first_seen` (первая встреча конвейера с файлом), не mtime.

**Причина:** удалять «без показа» гигабайты нельзя — режим просмотра по умолчанию. Имена файлов в
хранилище зависят от mtime и папки заметок на момент рендера — угадывать их потом ненадёжно,
поэтому они в БД. mtime меняется при копировании; первая встреча — нет.

**Последствия:** заметки, сделанные до этой версии, в `outputs` не записаны: их аудио в хранилище
`prune` не видит, пока запись не прогнана ещё раз (из кэша — мгновенно). Подзадача «не хранить wav
ингеста после прогона» отложена: стадия ингеста вызывается в каждом прогоне, и без wav повторный
прогон перестал бы быть мгновенным; со сроком хранения кэш и так ограничен.

## 2026-10-28 — Меню: нумерованные пункты без библиотеки, настройки — в тот же `.env` (#38)
**Контекст:** `summuraze` без аргументов должен открывать меню (записать / из файла / последние
заметки / настройки), не ломая `--help`, подкоманды и запуск из скриптов. Своей логики конвейера
у меню быть не должно.

**Решение:**
- Пункты — нумерованный список через `typer.prompt`, без библиотеки меню (questionary и т. п.).
  Меню зовёт `cli._run` / `cli._record` — те же функции, что подкоманды.
- Не терминал (pipe, CI) — подсказка про подкоманды и код 2, а не ожидание ввода.
- «Из файла»: последние записи из `SUMMURAZE_RECORD_DIR`, окно `zenity` (если есть дисплей)
  или путь — в кавычках, с `\ `, `file://` при перетаскивании в терминал.
- «Последние заметки» — `*.md` папки заметок по mtime; открытие — `xdg-open obsidian://open?path=…`,
  если задана папка хранилища, иначе сам `.md`.
- «Настройки» (API ↔ локально, папка заметок) — запись в `.env` на месте: комментарии и порядок
  строк остаются. После записи конфиг перечитывается: не прошло валидацию (`local_only` + API) —
  `.env` откатывается; значение перекрыто переменной окружения — меню говорит об этом.
- Строка стадии в терминале тикает секундомером (`[3/6] распознавание… 04:12`) — для меню и
  подкоманд одинаково; в pipe — только итог.

**Причина:** стрелки не стоят новой зависимости на медленном канале, а цифры проверяются через
`CliRunner` как есть. Второй файл настроек был бы вторым источником истины рядом с `.env` (#3).
typer 0.27 вшивает свою копию click — `click.Abort`/`IntRange` из пакета `click` с ней не
совместимы, поэтому ввод проверяется своим кодом.

**Последствия:** `.env` ищется в текущем каталоге (как и раньше у конфига) — меню работает из
папки проекта. Заодно найден баг #37: после Ctrl+C в записи SIGINT оставался игнорируемым, и
конвейер после записи не прерывался — `_absorb_echoed_sigint` теперь ставит обычный обработчик.

## 2026-10-28 — Запись: один ffmpeg, две дорожки Opus в потоковом Matroska (#37)
**Контекст:** `summuraze record` должен писать микрофон и звук системы раздельно (для этапа 6),
не терять запись при падении и сразу показывать немой источник. Ручная запись `pw-record` в wav —
115 МБ/час (#49).

**Решение:**
- Один процесс ffmpeg, входы `-f pulse` (PipeWire через pipewire-pulse): микрофон и монитор
  вывода по умолчанию (`pactl`), переопределяются `SUMMURAZE_RECORD_MIC/SYSTEM`.
- Файл `.mka`, Opus 32 кбит/с на дорожку (~29 МБ/час на обе), подписи дорожек «микрофон» /
  «система». Режим `-live 1`, кластер 1 с, `-flush_packets 1`; после штатной остановки —
  перепаковка без перекодирования, чтобы дописать длительность и индекс.
- Уровни считает тот же ffmpeg (`astats` → `ametadata ... direct=1` в stdout, 4 раза в секунду):
  индикатор, предупреждение «тишина 10 с» по дорожке, предупреждение о выключенном источнике
  ещё до старта, авто-стоп после 15 минут тишины на всех дорожках.
- До записи — `preflight` конвейера (профиль, словарь, ключ LLM, папка заметок): ошибка в
  конфиге видна до пары, а не после.
- ffmpeg — в своей группе процессов, остановка — `q` в stdin. Повторный SIGINT в первые 2 с
  после остановки глотается.

**Причина:** замер на живом PipeWire. Без потокового режима ffmpeg держал всё в буфере: `kill -9`
через 6 с — пустой файл; с ним — теряется ≤ 1 с. `ametadata` без `direct=1` буферизует вывод —
индикатор молчал. Под `uv run` Ctrl+C приходит дважды (от терминала и пересланный uv) — второй
убивал конвейер сразу после записи.

**Последствия:** онлайн-лекция **через колонки**: микрофон пишет эхо системного звука, и при
сведении дорожек (ингест, ADR #5) Whisper получает кашу — на синтетике вместо фразы вышло
«Продолжение следует...», по отдельности обе дорожки распознаются. Пока: наушники или
`--stream 1`; выбор дорожки автоматически — после замера на живой речи. Тесты CI подменяют
`-f pulse` на `lavfi` — команда, уровни и остановка те же.

## 2026-10-28 — OpenRouter: без fp4-провайдеров; правила разделов конспекта; мысль — один раз (#17)
**Контекст:** первая живая запись (3 мин, лекция о GC в Go). Распознавание чистое, но в конспекте
«Формулы и примеры», «Вопросы и ответы» и «Что почитать» заполнены копиями тезисов и выдуманными
вопросами. После уточнения промпта следующий прогон скопировал строки транскрипта во **все**
разделы. Повтор того же запроса на трёх провайдерах — документ нормальный. OpenRouter по
умолчанию берёт дешёвых провайдеров, часть из них — в fp4.

**Решение:**
- `provider.quantizations` = fp8 / bf16 / fp16 / fp32 / unknown (`SUMMURAZE_LLM_OPENROUTER_QUANTIZATIONS`,
  пусто — без фильтра).
- В промпте профиля «лекция» — что именно идёт в каждый раздел и «пустой список — правильный
  ответ»; версия профиля 3.
- Рендер выбрасывает повтор мысли (нормализованный текст) — страховка от сбойного провайдера.

**Причина:** строгая схема требует все поля, и слабая или сбойная модель скорее заполнит список,
чем оставит пустым. Промпт снимает первое, фильтр точности и дедупликация — второе.

**Последствия:** с фильтром цена та же порядка (~$0.002 за 3 мин). Если сбой повторится на
fp8 — следующий шаг: закрепить провайдера (`provider.order`) или модель посильнее.

**Контекст:** один адаптер на OpenRouter / DeepSeek / llama.cpp (ADR про OpenAI-совместимый

транскриптом — профиль в нём обнулял бы кэш при каждой смене профиля. Отказ до ASR — иначе час
Whisper впустую ради сообщения «нет ключа».

**Последствия:** с ноутбука OpenRouter доступен напрямую (проверено 2026-10-27), прокси нужен на
серверах в РФ. Тесты не читают `.env` разработчика (фикстура уходит в tmp) — иначе увидели бы
настоящий ключ. Первый живой прогон: голосовое 57 с — саммари за 28 с, $0.0005. Работу кэша
проверять по `cached_input` на прогоне того же транскрипта с другим профилем (#17).

## 2026-10-27 — Словарь терминов: `hotwords` ≤ 60 токенов, словарь на курс, замены поверх кэша (#13)
**Контекст:** план #13 — термины в `initial_prompt`. Открытый вопрос (QUESTIONS.md) — откуда брать
словарь: на проект, на курс, автосбор.

**Решение:**
- Термины идут в `hotwords` faster-whisper, а не в `initial_prompt`; подсказка ограничена
  60 токенами (~10–12 терминов). Что не влезло — отрезается с предупреждением в терминал.
- Словарь — текстовый файл или заметка Obsidian: строка = термин, `слышится -> пишется` = замена.
  Словарь курса (`--terms`) идёт первым, общий (`SUMMURAZE_ASR_TERMS_FILE`) — за ним. Автосбор
  из прошлых записей — не сейчас.
- Замены применяются к транскрипту поверх кэша (как детектор #12) и входят в ключ саммари; термины
  подсказки — в ключ ASR (без словаря ключ ASR прежний).

**Причина:** замер (BENCHMARKS.md, «Словарь терминов»): `initial_prompt` действует только на
первое 30-секундное окно — на поздние термины эффект ноль, `hotwords` — 4 → 15. Длиннее ~84
токенов распознавание теряет слова и вставляет непроизнесённые термины. Раз в подсказку
влезает десяток терминов, общий словарь на всё не работает — нужен свой на курс; длинный хвост
терминов закрывают замены, у них лимита нет.

**Последствия:** порядок в словаре — приоритет. На синтетике с подсказкой появились повторы
(«перейдём перейдём», дубль хвоста фразы) — проверить на живой лекции (#8/#9); если подтвердится,
выключать `condition_on_previous_text` при подсказке. Многословные замены не правят отдельные
слова (`Word`), только текст сегмента.

## 2026-10-27 — Галлюцинации Whisper ловятся по тексту, а не по уверенности; детектор — поверх кэша (#12)
**Контекст:** план #12 предполагал два вида сигналов: текст (шаблонные фразы, повторы n-грамм,
циклы между сегментами) и уверенность модели (`avg_logprob`, `no_speech_prob`). Замер на
large-v3-turbo: на тишине, тоне 440 Гц и шуме без VAD модель пишет «Продолжение следует...»
(язык ru) или «Thank you.» (en / автоопределение) — с `no_speech_prob` 0.00 и `avg_logprob`
−0.03…−0.23, то есть **увереннее, чем на настоящей речи**.

**Решение:**
- Основные правила — текстовые: шаблонные фразы (если они почти весь сегмент), титры
  субтитровщиков (всегда), одиночные «Спасибо.»/«Thank you.», повтор n-граммы подряд,
  сжимаемость текста > 2.4 (метрика самого Whisper), повтор соседнего сегмента от трёх слов.
  Пороги уверенности оставлены как дополнительный сигнал.
- Детектор — чистая функция поверх транскрипта из кэша; его `VERSION` входит в ключ саммари, а не
  ASR. Правка правил пересобирает саммари, но не стоит часа транскрибации.
- Сегмент помечается, не удаляется: в промпте — `[?]` и правило в system, в заметке —
  `⚠️ *текст* — причина`.

**Причина:** сигнал уверенности на типичных выдумках молчит. Пометка вместо удаления — ADR
2026-09-23 «VAD перед ASR».

**Последствия:** на чистом голосовом 57 с — ноль ложных срабатываний; на тишине/тоне/шуме — помечено
всё, что модель выдумала (тест `slow`). Одиночное «Спасибо.» в созвонах (этап 5) будет помечаться
зря — пересмотреть там. Список фраз пополняется по мере встречи на живых записях (поднимать
`VERSION`).

## 2026-10-27 — ASR: речь склеивается, таймкоды слов пересчитываются обратно; потоки = физ. ядра (#11)
**Контекст:** ASR получает интервалы речи от VAD (#10). У faster-whisper два способа их принять:
`clip_timestamps` (каждый интервал — свои окна по 30 с, таймкоды сразу в системе исходника) или
склейка речи в один массив с пересчётом таймкодов обратно (так устроен его `vad_filter`).

**Решение:**
- Склейка + пересчёт своим модулем `asr/timeline.py` (без вендора, свои тесты). Слово
  относится к куску склейки по середине; сегмент Whisper, слова которого легли в разные куски,
  режется по стыку. Встроенный `vad_filter` выключен.
- `SUMMURAZE_ASR_THREADS=0` — по числу физических ядер, а не дефолт CTranslate2 (4).
- После стадии ASR — `gc.collect()` + `malloc_trim(0)`.
- Дефолтный провайдер — `faster-whisper`; `echo` остался для тестов.

**Причина:** энкодер Whisper всегда считает 30-секундное окно. На двухчасовой лекции VAD даёт
~750 интервалов: с `clip_timestamps` это ≥ 750 проходов энкодера по полупустым окнам, со
склейкой — ~220. Потоки: на 5700U 8 потоков — RTF 0.43, 4 — 0.63 (BENCHMARKS.md). Память: без
`malloc_trim` glibc держит 1.1 ГБ кучи выгруженной модели, с ним — 0.24 ГБ; llama.cpp — отдельный
процесс, ему нужна память системы.

**Последствия:** без VAD Whisper на тишине пишет «Продолжение следует...» и пропускает речь
(проверено на синтетике) — `SUMMURAZE_VAD_ENABLED=false` только для диагностики. Одинаковые фразы
встык Whisper распознаёт один раз — в живой речи не встречается, но тестовые склейки собираются
из разных фраз. Проверка смещения на настоящей модели — `make test-all` (метка `slow`), в CI
модели нет.

## 2026-10-27 — VAD — Silero из состава faster-whisper; torch убран из зависимостей (#10)
**Контекст:** в ADR 2026-09-23 о версии Python VAD решили делать на torch-варианте пакета
`silero-vad`: своя ONNX-обёртка — ~50 строк и своя ответственность за корректность, а torch всё
равно понадобится `pyannote.audio` на этапе 5. При реализации #10 нашлось, что faster-whisper 1.2.1

**Решение:** `audio/vad.py` зовёт `faster_whisper.vad.get_speech_timestamps` (лениво, внутри
функции). Пакет `silero-vad` не ставим; torch из зависимостей убран до этапа 5, индекс

**Причина:** ноль новых зависимостей и минус torch с его 10 пакетами: `.venv` и время `uv sync`

**Последствия:** `faster_whisper.vad` — модуль без гарантий стабильности API; при обновлении

переселить на пакет `silero-vad`. Замер — BENCHMARKS.md: два часа за 28 с, пик 1.7 ГБ.

## 2026-10-23 — CI на Gitea Actions с порогом покрытия 85 %, без CD (#35)
**Контекст:** guardrail «lint и тесты зелёные перед коммитом» держался на честном слове: PR
сливались без серверной проверки. В плане CI не было ни на одном этапе — пропуск. Покрытие не
мерилось; замер на момент решения — 96 %.

## 2026-10-23 — Ингест сводит все аудиодорожки в одну по умолчанию (#5)
**Контекст:** в файле бывает несколько аудиодорожек: OBS пишет микрофон и звук системы отдельно,
в mkv бывают дорожки на разных языках. ffmpeg без явного `-map` берёт одну дорожку, и половина
разговора молча теряется.

**Решение:** без `--stream` все аудиодорожки сводятся `amix` с `normalize=0`. Конкретная дорожка
выбирается `--stream N`. Число дорожек сохраняется в `AudioInfo.audio_streams`. Выход
детерминирован (`-map_metadata -1`, bitexact): один вход даёт одинаковые байты.

**Причина:** потерять речь хуже, чем получить лишнюю дорожку: лишнее видно сразу, потерянное нет.
`normalize=0` — потому что при нормализации amix делит громкость на число дорожек, и тихий
собеседник становится ещё тише для VAD. Детерминизм нужен, чтобы хеш wav мог служить ключом кэша
следующих стадий (#6).

**Последствия:** для mkv с дублирующими языковыми дорожками сведение даст кашу — тогда `--stream`.
Раздельная обработка дорожек (атрибуция спикеров) — этап 6; число дорожек для неё уже есть.

## 2026-09-23 — Python 3.14 как рабочая версия, torch — только с индекса CPU (#1)
**Контекст:** в системе стоит Python 3.14, и план исходил из того, что под него колёс
`ctranslate2`/`torch` скорее всего нет, а фолбэком будет 3.12. Замер показал обратное. Проверялось
через `uv pip install --dry-run --no-build`: флаг запрещает сборку из исходников, поэтому успешный
резолв означает «готовое колесо есть».

**Результат замера (2026-09-23, uv 0.8.4).** Все 14 пакетов планируемого стека имеют колёса и под
3.14, и под 3.12: `ctranslate2`, `faster-whisper`, `onnxruntime`, `torch`, `torchaudio`,
`silero-vad`, `typer`, `pydantic-settings`, `fastapi`, `uvicorn`, `httpx`, `loguru`, `openai`,
`pyannote.audio`. Поимённо сверены версии шести из них — под 3.14 берутся **последние**, без
откатов назад: ctranslate2 4.8.2, faster-whisper 1.2.1, onnxruntime 1.30.0, silero-vad 6.2.3,
fastapi 0.141.1, pydantic-settings 2.15.0.

Для `pyannote.audio` известно только то, что он резолвится под 3.14 — конкретная версия не
измерена: повторный прогон упал на сетевой ошибке (`Failed to fetch .../simple/sqlalchemy/`).
Под 3.12 он даёт `pyannote-audio==4.0.7` и дерево из 111 пакетов. На выбор версии Python это не
влияет: diarization нужна только на этапе 5 (#25), и к тому моменту дерево всё равно
перепроверяется.

**Отдельная находка про torch.** С PyPI по умолчанию `torch` тянет 29 пакетов, из них **15 —
`nvidia-*`** (CUDA 13: cublas, cudnn, cufft, nccl и прочее). На машине без дискретной NVIDIA это
несколько гигабайт мёртвого груза. С индекса `https://download.pytorch.org/whl/cpu` — 10 пакетов,
ни одного nvidia, `torch==2.14.0+cpu`.

**Отдельная находка про VAD.** Подзадача «взять ONNX-вариант Silero и не тащить torch» не решается
пакетом: у `silero-vad` 6.2.3 зависимость `torch>=1.12.0` **безусловная**, extra `onnx-cpu` лишь
добавляет `onnxruntime`, но torch не убирает. Обойтись без torch можно только своей тонкой
обёрткой над `silero_vad.onnx` из состава пакета — это ~50 строк кода и своя ответственность за
корректность (кадры по 512 сэмплов, состояние LSTM).

**Решение:** `.python-version` = **3.14** (системный интерпретатор, ничего лишнего не ставим);
`requires-python = ">=3.12,<3.15"`; torch прибит к индексу `pytorch-cpu` через `tool.uv.sources`;
ruff и mypy целятся в **3.12**, а не 3.14. VAD пока на torch-варианте Silero, своя ONNX-обёртка —
не сейчас.

**Причина:** причин брать более старую версию не нашлось — ни одна зависимость её не требует, и
3.14 не откатывает пакеты назад. Системный интерпретатор снимает необходимость качать и
поддерживать второй (на этой машине скачивание 3.13 через uv так и не завершилось). Индекс CPU для
torch — не оптимизация, а защита от того, что кто-то в задаче #2 молча притащит гигабайты CUDA.
Цель линтера 3.12 при разработке на 3.14 — чтобы код не оброс синтаксисом, из-за которого откат на
фолбэк стал бы невозможен: фолбэк должен остаться настоящим, а не декларативным. Отвергнуто: 3.12
по умолчанию (нет причины), своя ONNX-обёртка ради экономии torch (torch всё равно нужен
`pyannote.audio` на этапе 5 — экономия мнимая).

**Последствия и что осталось непроверенным:** замер показывает, что колёса **скачиваются**, но не
что они **работают**. Проверку в рантайме (установка + прогон faster-whisper на реальной русской
речи) выполнить не удалось: канал в момент работы деградировал до ~28 КБ/с до PyPI,
~253 Б/с до HuggingFace (откуда идут модели Whisper) и полного таймаута до собственного Gitea по
HTTPS. При таком канале ядро STT (~150 МБ) ставится часами. Проверка обязательна до закрытия
задачи #2 — команда и критерий в issue #1. Если на 3.14 что-то сломается в рантайме, откат на 3.12
готов: интерпретатор уже на диске, `requires-python` и цель линтера его допускают, менять
ограничения в коде не придётся.

## 2026-09-23 — Кэш артефактов по стадиям как архитектурное требование
**Контекст:** на этом железе (см. [`ARCHITECTURE.md`](ARCHITECTURE.md)) ASR часа записи — десятки
минут CPU. Саммаризация того же часа — минуты по API. Итерации при разработке и в работе идут
почти целиком по промптам и профилям, то есть по дешёвой стадии.
**Решение:** каждая стадия конвейера — чистая функция «артефакт → артефакт», результат пишется на
диск, ключ = `sha256(входной артефакт + версия стадии + значимые параметры)`. Транскрипт —
самостоятельный артефакт, а не промежуточный буфер.
**Причина:** без этого любая правка промпта стоит 25 минут ожидания, и итерации по качеству
саммари просто не случатся. Дешевле спроектировать сразу, чем пришивать кэш к готовому конвейеру.
**Последствия:** версия стадии — часть контракта; менять логику стадии, не меняя версию, нельзя.
Нужен GC старых артефактов (аудио + модели быстро съедают десятки ГБ).

## 2026-09-23 — Один OpenAI-совместимый адаптер для локального и API-пути; дефолт — DeepSeek
**Контекст:** требование пользователя — переключаться между локальной моделью и API. Первый набросок
плана закладывал Claude как дефолт и три отдельных адаптера (anthropic / openai_compat / local).
Сверка с api-docs.deepseek.com (2026-09-23): `deepseek-flash` (V4.1-Flash) — контекст 1M, выход
384K, $0.15/$0.60 за млн off-peak, кэш-хит $0.003. Двухчасовая лекция ≈ **$0.01**, против ~$0.30
на `claude-opus-5` при том же 1M контекста. Отдельно: алиас `deepseek-chat` retired 24.07.2026.
**Решение:** один адаптер `openai_compat.py`. DeepSeek, OpenRouter, Yandex AI Studio и локальный
llama.cpp/Ollama говорят по одному протоколу, поэтому переключение — это `base_url` + `model` +
`api_key` в конфиге, а не ветка в коде. Дефолт — `deepseek-flash`. `anthropic_llm.py` — отдельный
опциональный адаптер, заводим только если понадобится сравнить качество.
**Причина:** требование «переключаться» реализуется почти бесплатно именно потому, что локальный
llama.cpp server отдаёт OpenAI-совместимый API — тот же код обслуживает оба пути, и локальный режим
не вырождается в заброшенную ветку, которая «когда-нибудь заработает». Разница в цене 30× при
одинаковом контексте не оставляет Claude шансов на роль дефолта. Отвергнуто: три адаптера
(дублирование), Claude по умолчанию (цена), только локально (медленно и слабее по структурированию).
**Последствия:** ID моделей провайдера сверяем в момент реализации, а не по памяти — отсюда
guardrail #9. Порог перехода на иерархическую свёртку становится свойством провайдера в конфиге
(1M у DeepSeek против, например, 128K у других), а не константой. Кэш префикса у провайдеров
устроен по-разному (автоматический у DeepSeek, prompt cache у llama.cpp) — правило остаётся
провайдеро-независимым: транскрипт первым и байт в байт, изменчивое после него.

## 2026-09-23 — Начинаем с лекций на один голос; многоголосые записи — отдельным этапом
**Контекст:** заявленные типы записей — созвоны, лекции, встречи, семинары. Атрибуция спикеров на
CPU дорога (diarization сравнима по времени с самим ASR), а профили созвона и встречи без «кто
сказал» почти бесполезны: действие без исполнителя — не действие.
**Решение:** этапы 0–4 делают систему для **одного говорящего**: профили «лекция» и «сырой»,
никакой атрибуции. Многоголосый случай — этап 5 целиком: diarization, сопоставление имён и профили
созвона / встречи / семинара вместе.
**Причина:** так первый полезный документ появляется в разы раньше. Если бы спикеры шли ранним
этапом, пришлось бы платить самой дорогой стадией конвейера до того, как проверено главное — что
саммари вообще читается вместо записи. Сборка «diarization + профили обсуждения» в один этап — не
лень, а связность: они бессмысленны по отдельности.
**Последствия:** `Segment.speaker` остаётся в контракте с самого начала (`None` до этапа 5) —
дописывать поле в кэшированные артефакты потом дороже, чем завести сразу.

## 2026-09-23 — Single-pass как основной режим, иерархическая свёртка — фолбэк
**Контекст:** привычный рецепт для саммари длинного текста — map-reduce по чанкам. Но контекст
дефолтного провайдера (`deepseek-flash`, 1M токенов) вмещает запись целиком: час русской речи
≈ 16–20 тыс. токенов, двухчасовая лекция — менее 5 % контекста.
**Решение:** если транскрипт влезает в бюджет — один запрос на весь транскрипт. Окна и свёртка
включаются только когда не влезает, и тогда двухпроходно: сначала карта разделов, потом финальный
документ по карте плюс полный транскрипт.
**Причина:** свёртка по чанкам систематически теряет то, ради чего саммари и нужно: связь между
вопросом в начале и ответом в конце, изменение решения по ходу разговора, возврат к теме.
Чанкинг — не бесплатная техника, а потеря качества, и применять её надо только когда иначе никак.
**Последствия:** нужен реальный счётчик токенов, а не эвристика по символам — и замер коэффициента
для русского текста. Порог — свойство провайдера в конфиге: у локальной 8B-модели контекст на два
порядка меньше, чем у `deepseek-flash`, и там свёртка включится на обычной лекции.

## 2026-09-23 — Спикеры: раздельные дорожки как основной путь, diarization-модель — опция
**Контекст:** diarization на CPU — дорогая стадия, сравнимая по времени с самим ASR. При этом
типичный созвон — это «я и остальные», а система уже умеет писать микрофон и монитор вывода
раздельно (PipeWire есть).
**Решение:** основной путь сепарации — раздельные дорожки при записи. Diarization-модель — по
флагу, для «много людей в одной комнате».
**Причина:** два трека дают точную атрибуцию бесплатно и без ошибок кластеризации. Платить часом
CPU за то, что уже известно из способа записи, незачем.
**Последствия:** `record` обязан писать две дорожки с самого начала — иначе привезённый файл уже
не разделить. Для чужих записей (одна дорожка) остаётся только модель.

## 2026-09-23 — VAD перед ASR, не после
**Контекст:** Whisper на тишине и на музыке генерирует текст, которого не было — циклы,
«Спасибо за просмотр», повторы последней фразы. В записи созвона тишины бывает 20–40 %.
**Решение:** Silero VAD выделяет интервалы речи, ASR получает только их. Плюс детектор повторов
как вторая линия — помечает сомнительные сегменты, не удаляя.
**Причина:** это одновременно ускорение (не расшифровываем тишину) и главный способ убрать
основной источник галлюцинаций STT. Пометка вместо удаления — потому что «здесь плохо слышно»
должно дойти до промпта саммари: модель не должна достраивать смысл по битому тексту.
**Последствия:** таймкоды считаются от начала исходного файла, а не от начала склейки речевых
интервалов — иначе вся навигация по саммари врёт.

## 2026-09-23 — SQLite для состояния, файлы для артефактов
**Контекст:** нужно хранить задачи, статусы, историю прогонов, стоимость.
**Решение:** SQLite для метаданных, файлы на диске для артефактов (аудио, транскрипты, саммари).
**Причина:** один пользователь, одна машина, нет конкурентной записи. Postgres здесь — контейнер,
который надо поднять перед тем как расшифровать лекцию. Артефакты в БД не кладём: их нужно
открывать глазами и внешними инструментами.
**Последствия:** если появится многопользовательский режим — миграция на Postgres; слой `store/`
для этого изолирован.
