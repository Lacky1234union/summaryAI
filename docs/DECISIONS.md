# Архитектурные решения (ADR)

## 2026-10-27 — LLM: OpenRouter по умолчанию, адаптер на httpx, транскрипт перед профилем (#15)
**Контекст:** один адаптер на OpenRouter / DeepSeek / llama.cpp (ADR про OpenAI-совместимый
протокол). Кэш префикса удешевляет вход в 50 раз, но только при совпадающем начале запроса.
Пользователь 2026-10-27 решил: один ключ OpenRouter на все проекты (meditron, vobot, tgit),
отдельный аккаунт DeepSeek не заводить. OpenRouter режет IP из РФ (опыт vobot).

**Решение:**
- Дефолт — **OpenRouter**: `https://openrouter.ai/api/v1`, `deepseek/deepseek-v4.1-flash` (та же
  V4.1-Flash, что `deepseek-flash` у DeepSeek; сверено 2026-10-27). Ключ — `OPENROUTER_API_KEY`
  (или `SUMMURAZE_LLM_API_KEY`), прокси — `SUMMURAZE_LLM_PROXY_URL` / `LLM_PROXY_URL` /
  `OPENROUTER_PROXY_URL`, http или socks5: имена те же, что в остальных проектах.
- `summarize/openai_compat.py` на `httpx` (один POST `/chat/completions`), без SDK `openai`.
- Сообщения: `system` — общая постоянная строка; `user` — транскрипт байт в байт, затем промпт
  профиля и вопрос. Промпт профиля в `system` не кладём.
- Стоимость — `usage.cost`, которую возвращает OpenRouter. Для DeepSeek напрямую — таблица
  `summarize/pricing.py` с часами пик (01–04, 06–10 UTC, пн–пт — вдвое дороже). Неизвестная
  модель — цена «—», локальный сервер — 0.
- Ретраи только на 408/429/5xx и таймаут (3 попытки); 401/402/403/404 — сразу ошибка с подсказкой.
- Нет ключа для внешнего адреса → отказ в начале прогона, до транскрибации.

**Причина:** один ключ — меньше аккаунтов и `.env`. SDK не знает DeepSeek-полей кэша
(`prompt_cache_hit_tokens`) и тянет зависимости ради одного запроса. `system` стоит перед
транскриптом — профиль в нём обнулял бы кэш при каждой смене профиля. Отказ до ASR — иначе час
Whisper впустую ради сообщения «нет ключа».

**Последствия:** с ноутбука OpenRouter доступен напрямую (проверено 2026-10-27), прокси нужен на
серверах в РФ. Тесты не читают `.env` разработчика (фикстура уходит в tmp) — иначе увидели бы
настоящий ключ. Первый живой прогон: голосовое 57 с — саммари за 28 с, $0.0005. Работу кэша
проверять по `cached_input` на прогоне того же транскрипта с другим профилем (#17).

## 2026-10-27 — Словарь терминов: `hotwords` ≤ 60 токенов, словарь на курс, замены поверх кэша (#13)
**Контекст:** план #13 — термины в `initial_prompt`. Открытый вопрос (QUESTIONS.md) — откуда брать
словарь: на проект, на курс, автосбор.

**Решение:**
- Термины идут в `hotwords` faster-whisper, а не в `initial_prompt`; подсказка ограничена
  60 токенами (~10–12 терминов). Что не влезло — отрезается с предупреждением в терминал.
- Словарь — текстовый файл или заметка Obsidian: строка = термин, `слышится -> пишется` = замена.
  Словарь курса (`--terms`) идёт первым, общий (`SUMMURAZE_ASR_TERMS_FILE`) — за ним. Автосбор
  из прошлых записей — не сейчас.
- Замены применяются к транскрипту поверх кэша (как детектор #12) и входят в ключ саммари; термины
  подсказки — в ключ ASR (без словаря ключ ASR прежний).

**Причина:** замер (BENCHMARKS.md, «Словарь терминов»): `initial_prompt` действует только на
первое 30-секундное окно — на поздние термины эффект ноль, `hotwords` — 4 → 15. Длиннее ~84
токенов распознавание теряет слова и вставляет непроизнесённые термины. Раз в подсказку
влезает десяток терминов, общий словарь на всё не работает — нужен свой на курс; длинный хвост
терминов закрывают замены, у них лимита нет.

**Последствия:** порядок в словаре — приоритет. На синтетике с подсказкой появились повторы
(«перейдём перейдём», дубль хвоста фразы) — проверить на живой лекции (#8/#9); если подтвердится,
выключать `condition_on_previous_text` при подсказке. Многословные замены не правят отдельные
слова (`Word`), только текст сегмента.

## 2026-10-27 — Галлюцинации Whisper ловятся по тексту, а не по уверенности; детектор — поверх кэша (#12)
**Контекст:** план #12 предполагал два вида сигналов: текст (шаблонные фразы, повторы n-грамм,
циклы между сегментами) и уверенность модели (`avg_logprob`, `no_speech_prob`). Замер на
large-v3-turbo: на тишине, тоне 440 Гц и шуме без VAD модель пишет «Продолжение следует...»
(язык ru) или «Thank you.» (en / автоопределение) — с `no_speech_prob` 0.00 и `avg_logprob`
−0.03…−0.23, то есть **увереннее, чем на настоящей речи**.

**Решение:**
- Основные правила — текстовые: шаблонные фразы (если они почти весь сегмент), титры
  субтитровщиков (всегда), одиночные «Спасибо.»/«Thank you.», повтор n-граммы подряд,
  сжимаемость текста > 2.4 (метрика самого Whisper), повтор соседнего сегмента от трёх слов.
  Пороги уверенности оставлены как дополнительный сигнал.
- Детектор — чистая функция поверх транскрипта из кэша; его `VERSION` входит в ключ саммари, а не
  ASR. Правка правил пересобирает саммари, но не стоит часа транскрибации.
- Сегмент помечается, не удаляется: в промпте — `[?]` и правило в system, в заметке —
  `⚠️ *текст* — причина`.

**Причина:** сигнал уверенности на типичных выдумках молчит. Пометка вместо удаления — ADR
2026-09-23 «VAD перед ASR».

**Последствия:** на чистом голосовом 57 с — ноль ложных срабатываний; на тишине/тоне/шуме — помечено
всё, что модель выдумала (тест `slow`). Одиночное «Спасибо.» в созвонах (этап 5) будет помечаться
зря — пересмотреть там. Список фраз пополняется по мере встречи на живых записях (поднимать
`VERSION`).

## 2026-10-27 — ASR: речь склеивается, таймкоды слов пересчитываются обратно; потоки = физ. ядра (#11)
**Контекст:** ASR получает интервалы речи от VAD (#10). У faster-whisper два способа их принять:
`clip_timestamps` (каждый интервал — свои окна по 30 с, таймкоды сразу в системе исходника) или
склейка речи в один массив с пересчётом таймкодов обратно (так устроен его `vad_filter`).

**Решение:**
- Склейка + пересчёт своим модулем `asr/timeline.py` (без вендора, свои тесты). Слово
  относится к куску склейки по середине; сегмент Whisper, слова которого легли в разные куски,
  режется по стыку. Встроенный `vad_filter` выключен.
- `SUMMURAZE_ASR_THREADS=0` — по числу физических ядер, а не дефолт CTranslate2 (4).
- После стадии ASR — `gc.collect()` + `malloc_trim(0)`.
- Дефолтный провайдер — `faster-whisper`; `echo` остался для тестов.

**Причина:** энкодер Whisper всегда считает 30-секундное окно. На двухчасовой лекции VAD даёт
~750 интервалов: с `clip_timestamps` это ≥ 750 проходов энкодера по полупустым окнам, со
склейкой — ~220. Потоки: на 5700U 8 потоков — RTF 0.43, 4 — 0.63 (BENCHMARKS.md). Память: без
`malloc_trim` glibc держит 1.1 ГБ кучи выгруженной модели, с ним — 0.24 ГБ; llama.cpp — отдельный
процесс, ему нужна память системы.

**Последствия:** без VAD Whisper на тишине пишет «Продолжение следует...» и пропускает речь
(проверено на синтетике) — `SUMMURAZE_VAD_ENABLED=false` только для диагностики. Одинаковые фразы
встык Whisper распознаёт один раз — в живой речи не встречается, но тестовые склейки собираются
из разных фраз. Проверка смещения на настоящей модели — `make test-all` (метка `slow`), в CI
модели нет.

## 2026-10-27 — VAD — Silero из состава faster-whisper; torch убран из зависимостей (#10)
**Контекст:** в ADR 2026-09-23 о версии Python VAD решили делать на torch-варианте пакета
`silero-vad`: своя ONNX-обёртка — ~50 строк и своя ответственность за корректность, а torch всё
равно понадобится `pyannote.audio` на этапе 5. При реализации #10 нашлось, что faster-whisper 1.2.1
(уже стоит ради ASR) несёт `silero_vad_v6.onnx` и готовую разметку `faster_whisper.vad` —
ту самую обёртку, только чужую и проверенную его собственным `vad_filter`.

**Решение:** `audio/vad.py` зовёт `faster_whisper.vad.get_speech_timestamps` (лениво, внутри
функции). Пакет `silero-vad` не ставим; torch из зависимостей убран до этапа 5, индекс
`pytorch-cpu` в `pyproject.toml` оставлен для него.

**Причина:** ноль новых зависимостей и минус torch с его 10 пакетами: `.venv` и время `uv sync`
в CI заметно меньше. Модель та же — Silero v6. Принцип «зависимость приезжает со своим этапом»
(`pyproject.toml`) torch сейчас не проходит: кроме VAD, его никто не использует.

**Последствия:** `faster_whisper.vad` — модуль без гарантий стабильности API; при обновлении
faster-whisper тесты `test_vad.py` (речь espeak-ng на известной секунде) это поймают. VAD теперь
зависит от пакета ASR-адаптера: если ASR когда-нибудь уйдёт с faster-whisper, VAD придётся
переселить на пакет `silero-vad`. Замер — BENCHMARKS.md: два часа за 28 с, пик 1.7 ГБ.

## 2026-10-26 — В хранилище Obsidian кладётся сжатое аудио, а не оригинал (#18)
**Контекст:** таймкоды заметки ссылаются на запись. Хранилище `Worklive` синхронизируется через
Self-hosted LiveSync (CouchDB): часовой mp4 внутри — гигабайты на каждое устройство. Ссылка
`file:///` на оригинал вне хранилища ничего не синхронизирует, но работает только на ноутбуке.

**Решение:** рядом с заметкой кладётся аудио, пережатое в opus (~32 кбит/с, ~15 МБ/час);
таймкоды Media Extended ссылаются на него. Оригинал остаётся, где был.

**Причина:** заметку читают и на телефоне — там ссылка на ноутбучный файл мертва. 15 МБ на час
речи LiveSync переносит без проблем; для речи 32 кбит/с opus разборчив.

**Последствия:** новая стадия «аудио для заметки» (кэшируется как остальные). Битрейт —
в конфиге: если разборчивости не хватит, поднять без правки кода.

## 2026-10-26 — Obsidian — основной выход; меню и запись — этап 2.5; веб остаётся третьим интерфейсом
**Контекст:** в представлении пользователя продукт — CLI-утилита: запустил, выбрал «записать» или
«из файла», саммари легло в Obsidian. План расходился: Obsidian был экспортом в веб-интерфейсе
(этап 4), меню не было, запись — последним этапом (6), потому что задумывалась под созвоны.

**Решение:**
- Документ пишется **в Obsidian-хранилище с этапа 2** (`SUMMURAZE_OUTPUT_DIR`). Таймкоды — ссылки
  `#t=<сек>` для плагина Media Extended (4.2.9, установлен в хранилище `Worklive` 2026-10-26),
  рядом `.srt` для его интерактивного транскрипта.
- Новый **этап 2.5**: меню на голый `summuraze` и `summuraze record`. Запись сразу двумя
  дорожками (микрофон + звук системы).
- **Веб (этап 4) остаётся** — третьим интерфейсом к тому же ядру, а не заменой меню и Obsidian.
- Этап 6 сужается до атрибуции по уже записанным раздельным дорожкам.

**Причина:** Obsidian — место, где пользователь и так читает заметки; отдельная читалка в вебе
его дублировала бы. Запись лекции не нуждается в спикерах, поэтому ждать её до этапа 6 незачем.
Писать две дорожки с первого дня ничего не стоит: ингест их сводит (ADR #5), а этапу 6 они
нужны в исходном виде — потом файл уже не разделить.

**Последствия:** `render` знает про формат ссылок Media Extended — это адаптер вывода, а не ядро.
Открыт вопрос, где лежит медиа, на которое ссылаются таймкоды (LiveSync и гигабайты) —
`QUESTIONS.md`, решается в #18.
## 2026-10-23 — CI на Gitea Actions с порогом покрытия 85 %, без CD (#35)
**Контекст:** guardrail «lint и тесты зелёные перед коммитом» держался на честном слове: PR
сливались без серверной проверки. В плане CI не было ни на одном этапе — пропуск. Покрытие не
мерилось; замер на момент решения — 96 %.

**Решение:** `.gitea/workflows/ci.yml` на push и PR в `dev`/`main`: ffmpeg + `uv sync --locked` +
`make lint` + pytest с `pytest-cov`, порог `fail_under = 85`. Тесты `slow`/`eval` в CI не идут.
Раннер — общий self-hosted `studbank-act-runner` инстанса; свой на HSE — запасной вариант
(`docs/dev/CI_RUNNER.md`). Защита веток
требует статус `CI / lint-test (pull_request)`. Локальный эквивалент — `make ci`.

**Причина:** порог 85, а не 96 — адаптеры ASR и LLM будут проверяться в основном slow-тестами
с настоящими моделями, которых в быстром прогоне нет; высокий порог толкал бы к мокам, которые
проверяют сами себя. slow/eval вне CI — потому что модель выбирается замером на этом ноутбуке
(guardrail #7), а скорость на облачном CPU ничего о нём не говорит. ffmpeg ставится явно и
проверяется отдельным шагом: без него тесты ингеста молча ушли бы в skip под зелёной галкой.
`--locked` — расхождение `uv.lock` с `pyproject.toml` должно быть ошибкой PR, а не тихим
перерезолвом на сервере.

**Отвергнуто:** CD. Это локальная CLI-утилита — деплоить некуда. Сборка wheel по тегу при
промоушене `dev` → `main` — когда появится что выпускать.

**Последствия:** общий раннер делим с другими проектами — при очередях заводить свой.
CI блокирует слияние, только когда включена защита веток (шаг в Gitea, не в коде).
Переименование джоба в `ci.yml` требует правки правил защиты веток.

## 2026-10-23 — Ингест сводит все аудиодорожки в одну по умолчанию (#5)
**Контекст:** в файле бывает несколько аудиодорожек: OBS пишет микрофон и звук системы отдельно,
в mkv бывают дорожки на разных языках. ffmpeg без явного `-map` берёт одну дорожку, и половина
разговора молча теряется.

**Решение:** без `--stream` все аудиодорожки сводятся `amix` с `normalize=0`. Конкретная дорожка
выбирается `--stream N`. Число дорожек сохраняется в `AudioInfo.audio_streams`. Выход
детерминирован (`-map_metadata -1`, bitexact): один вход даёт одинаковые байты.

**Причина:** потерять речь хуже, чем получить лишнюю дорожку: лишнее видно сразу, потерянное нет.
`normalize=0` — потому что при нормализации amix делит громкость на число дорожек, и тихий
собеседник становится ещё тише для VAD. Детерминизм нужен, чтобы хеш wav мог служить ключом кэша
следующих стадий (#6).

**Последствия:** для mkv с дублирующими языковыми дорожками сведение даст кашу — тогда `--stream`.
Раздельная обработка дорожек (атрибуция спикеров) — этап 6; число дорожек для неё уже есть.

## 2026-09-23 — Python 3.14 как рабочая версия, torch — только с индекса CPU (#1)
**Контекст:** в системе стоит Python 3.14, и план исходил из того, что под него колёс
`ctranslate2`/`torch` скорее всего нет, а фолбэком будет 3.12. Замер показал обратное. Проверялось
через `uv pip install --dry-run --no-build`: флаг запрещает сборку из исходников, поэтому успешный
резолв означает «готовое колесо есть».

**Результат замера (2026-09-23, uv 0.8.4).** Все 14 пакетов планируемого стека имеют колёса и под
3.14, и под 3.12: `ctranslate2`, `faster-whisper`, `onnxruntime`, `torch`, `torchaudio`,
`silero-vad`, `typer`, `pydantic-settings`, `fastapi`, `uvicorn`, `httpx`, `loguru`, `openai`,
`pyannote.audio`. Поимённо сверены версии шести из них — под 3.14 берутся **последние**, без
откатов назад: ctranslate2 4.8.2, faster-whisper 1.2.1, onnxruntime 1.30.0, silero-vad 6.2.3,
fastapi 0.141.1, pydantic-settings 2.15.0.

Для `pyannote.audio` известно только то, что он резолвится под 3.14 — конкретная версия не
измерена: повторный прогон упал на сетевой ошибке (`Failed to fetch .../simple/sqlalchemy/`).
Под 3.12 он даёт `pyannote-audio==4.0.7` и дерево из 111 пакетов. На выбор версии Python это не
влияет: diarization нужна только на этапе 5 (#25), и к тому моменту дерево всё равно
перепроверяется.

**Отдельная находка про torch.** С PyPI по умолчанию `torch` тянет 29 пакетов, из них **15 —
`nvidia-*`** (CUDA 13: cublas, cudnn, cufft, nccl и прочее). На машине без дискретной NVIDIA это
несколько гигабайт мёртвого груза. С индекса `https://download.pytorch.org/whl/cpu` — 10 пакетов,
ни одного nvidia, `torch==2.14.0+cpu`.

**Отдельная находка про VAD.** Подзадача «взять ONNX-вариант Silero и не тащить torch» не решается
пакетом: у `silero-vad` 6.2.3 зависимость `torch>=1.12.0` **безусловная**, extra `onnx-cpu` лишь
добавляет `onnxruntime`, но torch не убирает. Обойтись без torch можно только своей тонкой
обёрткой над `silero_vad.onnx` из состава пакета — это ~50 строк кода и своя ответственность за
корректность (кадры по 512 сэмплов, состояние LSTM).

**Решение:** `.python-version` = **3.14** (системный интерпретатор, ничего лишнего не ставим);
`requires-python = ">=3.12,<3.15"`; torch прибит к индексу `pytorch-cpu` через `tool.uv.sources`;
ruff и mypy целятся в **3.12**, а не 3.14. VAD пока на torch-варианте Silero, своя ONNX-обёртка —
не сейчас.

**Причина:** причин брать более старую версию не нашлось — ни одна зависимость её не требует, и
3.14 не откатывает пакеты назад. Системный интерпретатор снимает необходимость качать и
поддерживать второй (на этой машине скачивание 3.13 через uv так и не завершилось). Индекс CPU для
torch — не оптимизация, а защита от того, что кто-то в задаче #2 молча притащит гигабайты CUDA.
Цель линтера 3.12 при разработке на 3.14 — чтобы код не оброс синтаксисом, из-за которого откат на
фолбэк стал бы невозможен: фолбэк должен остаться настоящим, а не декларативным. Отвергнуто: 3.12
по умолчанию (нет причины), своя ONNX-обёртка ради экономии torch (torch всё равно нужен
`pyannote.audio` на этапе 5 — экономия мнимая).

**Последствия и что осталось непроверенным:** замер показывает, что колёса **скачиваются**, но не
что они **работают**. Проверку в рантайме (установка + прогон faster-whisper на реальной русской
речи) выполнить не удалось: канал в момент работы деградировал до ~28 КБ/с до PyPI,
~253 Б/с до HuggingFace (откуда идут модели Whisper) и полного таймаута до собственного Gitea по
HTTPS. При таком канале ядро STT (~150 МБ) ставится часами. Проверка обязательна до закрытия
задачи #2 — команда и критерий в issue #1. Если на 3.14 что-то сломается в рантайме, откат на 3.12
готов: интерпретатор уже на диске, `requires-python` и цель линтера его допускают, менять
ограничения в коде не придётся.

## 2026-09-23 — Кэш артефактов по стадиям как архитектурное требование
**Контекст:** на этом железе (см. [`ARCHITECTURE.md`](ARCHITECTURE.md)) ASR часа записи — десятки
минут CPU. Саммаризация того же часа — минуты по API. Итерации при разработке и в работе идут
почти целиком по промптам и профилям, то есть по дешёвой стадии.
**Решение:** каждая стадия конвейера — чистая функция «артефакт → артефакт», результат пишется на
диск, ключ = `sha256(входной артефакт + версия стадии + значимые параметры)`. Транскрипт —
самостоятельный артефакт, а не промежуточный буфер.
**Причина:** без этого любая правка промпта стоит 25 минут ожидания, и итерации по качеству
саммари просто не случатся. Дешевле спроектировать сразу, чем пришивать кэш к готовому конвейеру.
**Последствия:** версия стадии — часть контракта; менять логику стадии, не меняя версию, нельзя.
Нужен GC старых артефактов (аудио + модели быстро съедают десятки ГБ).

## 2026-09-23 — Один OpenAI-совместимый адаптер для локального и API-пути; дефолт — DeepSeek
**Контекст:** требование пользователя — переключаться между локальной моделью и API. Первый набросок
плана закладывал Claude как дефолт и три отдельных адаптера (anthropic / openai_compat / local).
Сверка с api-docs.deepseek.com (2026-09-23): `deepseek-flash` (V4.1-Flash) — контекст 1M, выход
384K, $0.15/$0.60 за млн off-peak, кэш-хит $0.003. Двухчасовая лекция ≈ **$0.01**, против ~$0.30
на `claude-opus-5` при том же 1M контекста. Отдельно: алиас `deepseek-chat` retired 24.07.2026.
**Решение:** один адаптер `openai_compat.py`. DeepSeek, OpenRouter, Yandex AI Studio и локальный
llama.cpp/Ollama говорят по одному протоколу, поэтому переключение — это `base_url` + `model` +
`api_key` в конфиге, а не ветка в коде. Дефолт — `deepseek-flash`. `anthropic_llm.py` — отдельный
опциональный адаптер, заводим только если понадобится сравнить качество.
**Причина:** требование «переключаться» реализуется почти бесплатно именно потому, что локальный
llama.cpp server отдаёт OpenAI-совместимый API — тот же код обслуживает оба пути, и локальный режим
не вырождается в заброшенную ветку, которая «когда-нибудь заработает». Разница в цене 30× при
одинаковом контексте не оставляет Claude шансов на роль дефолта. Отвергнуто: три адаптера
(дублирование), Claude по умолчанию (цена), только локально (медленно и слабее по структурированию).
**Последствия:** ID моделей провайдера сверяем в момент реализации, а не по памяти — отсюда
guardrail #9. Порог перехода на иерархическую свёртку становится свойством провайдера в конфиге
(1M у DeepSeek против, например, 128K у других), а не константой. Кэш префикса у провайдеров
устроен по-разному (автоматический у DeepSeek, prompt cache у llama.cpp) — правило остаётся
провайдеро-независимым: транскрипт первым и байт в байт, изменчивое после него.

## 2026-09-23 — Начинаем с лекций на один голос; многоголосые записи — отдельным этапом
**Контекст:** заявленные типы записей — созвоны, лекции, встречи, семинары. Атрибуция спикеров на
CPU дорога (diarization сравнима по времени с самим ASR), а профили созвона и встречи без «кто
сказал» почти бесполезны: действие без исполнителя — не действие.
**Решение:** этапы 0–4 делают систему для **одного говорящего**: профили «лекция» и «сырой»,
никакой атрибуции. Многоголосый случай — этап 5 целиком: diarization, сопоставление имён и профили
созвона / встречи / семинара вместе.
**Причина:** так первый полезный документ появляется в разы раньше. Если бы спикеры шли ранним
этапом, пришлось бы платить самой дорогой стадией конвейера до того, как проверено главное — что
саммари вообще читается вместо записи. Сборка «diarization + профили обсуждения» в один этап — не
лень, а связность: они бессмысленны по отдельности.
**Последствия:** `Segment.speaker` остаётся в контракте с самого начала (`None` до этапа 5) —
дописывать поле в кэшированные артефакты потом дороже, чем завести сразу.

## 2026-09-23 — Single-pass как основной режим, иерархическая свёртка — фолбэк
**Контекст:** привычный рецепт для саммари длинного текста — map-reduce по чанкам. Но контекст
дефолтного провайдера (`deepseek-flash`, 1M токенов) вмещает запись целиком: час русской речи
≈ 16–20 тыс. токенов, двухчасовая лекция — менее 5 % контекста.
**Решение:** если транскрипт влезает в бюджет — один запрос на весь транскрипт. Окна и свёртка
включаются только когда не влезает, и тогда двухпроходно: сначала карта разделов, потом финальный
документ по карте плюс полный транскрипт.
**Причина:** свёртка по чанкам систематически теряет то, ради чего саммари и нужно: связь между
вопросом в начале и ответом в конце, изменение решения по ходу разговора, возврат к теме.
Чанкинг — не бесплатная техника, а потеря качества, и применять её надо только когда иначе никак.
**Последствия:** нужен реальный счётчик токенов, а не эвристика по символам — и замер коэффициента
для русского текста. Порог — свойство провайдера в конфиге: у локальной 8B-модели контекст на два
порядка меньше, чем у `deepseek-flash`, и там свёртка включится на обычной лекции.

## 2026-09-23 — Спикеры: раздельные дорожки как основной путь, diarization-модель — опция
**Контекст:** diarization на CPU — дорогая стадия, сравнимая по времени с самим ASR. При этом
типичный созвон — это «я и остальные», а система уже умеет писать микрофон и монитор вывода
раздельно (PipeWire есть).
**Решение:** основной путь сепарации — раздельные дорожки при записи. Diarization-модель — по
флагу, для «много людей в одной комнате».
**Причина:** два трека дают точную атрибуцию бесплатно и без ошибок кластеризации. Платить часом
CPU за то, что уже известно из способа записи, незачем.
**Последствия:** `record` обязан писать две дорожки с самого начала — иначе привезённый файл уже
не разделить. Для чужих записей (одна дорожка) остаётся только модель.

## 2026-09-23 — VAD перед ASR, не после
**Контекст:** Whisper на тишине и на музыке генерирует текст, которого не было — циклы,
«Спасибо за просмотр», повторы последней фразы. В записи созвона тишины бывает 20–40 %.
**Решение:** Silero VAD выделяет интервалы речи, ASR получает только их. Плюс детектор повторов
как вторая линия — помечает сомнительные сегменты, не удаляя.
**Причина:** это одновременно ускорение (не расшифровываем тишину) и главный способ убрать
основной источник галлюцинаций STT. Пометка вместо удаления — потому что «здесь плохо слышно»
должно дойти до промпта саммари: модель не должна достраивать смысл по битому тексту.
**Последствия:** таймкоды считаются от начала исходного файла, а не от начала склейки речевых
интервалов — иначе вся навигация по саммари врёт.

## 2026-09-23 — SQLite для состояния, файлы для артефактов
**Контекст:** нужно хранить задачи, статусы, историю прогонов, стоимость.
**Решение:** SQLite для метаданных, файлы на диске для артефактов (аудио, транскрипты, саммари).
**Причина:** один пользователь, одна машина, нет конкурентной записи. Postgres здесь — контейнер,
который надо поднять перед тем как расшифровать лекцию. Артефакты в БД не кладём: их нужно
открывать глазами и внешними инструментами.
**Последствия:** если появится многопользовательский режим — миграция на Postgres; слой `store/`
для этого изолирован.
